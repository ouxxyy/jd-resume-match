# 整份简历分析策略（0.3.0）

输入仅为用户提供的简历、JD 与本轮回答；不默认调研公司。评分按 scoring-rubric，表达按 content-standards。本规范决定定性分析的过程与产物，不新增加减分标准。

## 1. 先理解岗位，再盘点全篇

1. 提炼最多十个互不重复的关键概念，每个引用未合并的主目标要求及 JD 原文。不够十个就交更少。分别指出岗位要的工作、技能与证明它们的行为；关键词命中不是能力判断。
2. 基于岗位职责解释可能的招聘业务问题，明确标为推断；JD 未说明的目标、痛点或指标记为待确认。不得宣称知道公司真正想法。
3. 按原材料盘点所有非联系方式内容：模块→经历→条目。教育、课程、实习、项目、工作、校园、技能、自评等都要有去向；没有某模块不生成假模块。联系方式不进入库存或分享文案。测试文档的通用标题、synthetic 声明属于文档封套，不算候选人经历，也不列为待补事实。
4. 对每项给出保留、前置、压缩或删除及理由，分别说明相关经历、低相关内容、空间价值低的重复描述和遗漏证据。低相关任职保留雇主、职位、日期，压缩职责，而不制造履历缺口。

完成标准：所有非联系方式内容均已盘点，重点概念能回到 JD 原文，现有事实与业务推断分开。

## 2. 排整份结构

- 优先展示核心岗位要求的直接证据，然后考虑覆盖完整程度、成果强度和时效性；相同条件保留原序。排序是定性编辑判断，不产生另一套分数。
- 模块、经历、条目都要排序。较早但相关的整段经历可以前移，日期仍可见；条目不能移动到其他经历。模块可重新组织经历，但原雇主、职位和日期关系始终保留。
- 根据实际证据选择教育、实习、项目或工作优先；资历只影响关注点。应届项目可能最有价值，研究或资格导向岗位的教育也可能应在前；工作年限不会自动证明管理能力。
- 明确说明新结构的开头应让读者看到哪条证据、哪些内容后移或压缩。只交结构方案和重点改写，不额外交一份完整重写简历。
- 原序是提取文本顺序；没看到原始视觉材料时不得说已还原真实版面或首屏。用“简历开头的文本”与“速读视角”，不把十几秒包装成所有招聘方的固定时限。

完成标准：蓝图同时给出模块顺序、经历顺序、条目顺序，每个保留项出现一次，删除项有理由。

## 3. 深挖关键经历，审阅风险

- 全篇评相关性，仅深挖能证明核心要求的关键经历。逐段辨认：问题、本人角色、具体行动、产出、发生的变化、展示的技能、对业务/团队/客户/时间/成本/收入的影响。
- 原文写了什么就证明什么；缺指标可以写可核对的产出、使用场景与作用，不把“参与某任务”改成“提升某指标”。团队成果仍属于团队，时间先后不等于个人因果，职责范围按原文保留。事实字段只写已确认的角色与行动，职责范围是否更大另放 question 或待补清单，避免把未知范围词混进 fact；校验器保守检查职责词，不靠猜测语言否定关系豁免。
- 对缺失环节列“补什么、去哪里找”：交付记录、周报、上线记录、反馈、前后口径一致的数据等。追问仍为一轮最多三问且可跳过，优先门槛、个人贡献、结果口径；其余留在待补清单。
- 招聘者审阅覆盖：开头传递的信息、被埋没的强证据、泛泛表述、筛选疑虑。疑虑给原文依据、具体位置、待核实事实/面试追问及改法；批评句子与结构，不否定人格或断言实际拒绝。
- 关键词诊断区分原文已有、同义表达、已有经验未写清、缺少证据。检查模糊术语、章节命名和文本阅读顺序；原始视觉版式未核验时，双栏、字体、图像或具体 ATS 系统解析能力都保持未核验。

完成标准：深挖没有新增事实，疑虑有引用与追问，关键词缺失没有变成能力否定。

## 4. 数据约束与改写

新版 editorial 的 `resume_strategy` 是唯一载体，字段定义见 editorial.schema.json；报告/rubric 仍为 0.1.0。

- `inventory`：每项稳定 `item_id`，`kind=section/entry/bullet`，`parent_id` 与每个父级内连续的 `original_order`。`raw_quote` 必须是 `evidence_ids` 引文的连续子串；经历声明 `entry_kind`。工作/实习的 raw_quote 保留完整任职引文；标签简写时蓝图另展示原文任职信息，保留雇主、职位和日期，引用不包含联系方式。全篇引文可增加到 report.evidence，闲置证据不计分。
- `blueprint`：数组顺序就是新顺序。引用模块 ID、经历 ID 和有序条目 ID；所有非 omit 项必须出现一次，omit 项不能混入蓝图。经历可以跨模块编排；条目保持原经历。根层及每层的原序均连续。
- 通用判断形状：`{text, basis, req_ids, evidence_ids, answer_ids, item_ids}`。`basis=fact/inference/question` 分别展示“原文已有/推断/待确认”；数组可为空，但至少有一种锚点，事实必须有原文引用。要求仅引用未合并的主目标要求。
- `job_focus` 记录概念、要求、逐字 JD 摘录和 `business_problem` 判断；业务问题仅允许 inference/question。`experience_insights` 为关键经历的七个价值链判断。
- `recruiter_review` 包含开头印象、埋没证据、泛泛表述、疑虑；每条疑虑的 observation 用通用判断，另有 interview_question 与 change。`ats_review` 包含关键词状态、文本可读性与格式观察，明确 format_status。
- 补充回答不等于原简历事实。通过 `answer_links=[{answer_id, entry_id}]` 关联具体经历；未关联回答不能证明某段经历的职责或数字。一个回答跨经历时逐项说明事实，避免把混合回答整体归给每段。
- `revision_priorities` 按风险与影响给连续 order、具体 change、location_item_ids、impact 与 rewrite_ids。覆盖全部有效改写；每条改写关联唯一经历，并明确它在蓝图里的位置。原报告三项 actions 的顺序仍遵守评分/表达契约，不随修改建议列表改口径。
- 改写仍只用 report.rewrites；不足三处就更少，不新增第六个有效改写。数字、职责词只引用同一经历的证据，不从其他经历、JD 或报告分数借数字；改前原句必须来自该经历。单位、归属和因果保真仍需语义审阅，数字词面校验不是语义正确证明。
- `missing_facts` 每条有 gap、ask、where_to_find 与位置/要求引用。待补问法不填造指标或成果，不混入可复制简历文本。

## 5. 展示与版本

HTML 沿用既有 CSS：结论→发现→整份结构方案→重点改写→行动→证据。原/新结构及修改优先级直接展示；全篇盘点、岗位重点、价值链、招聘审阅、关键词诊断、待补清单默认折叠。新内容按报告私有件处理，所有可见字符串经过转义和声明的 redactions，不自动塞入分享卡。

0.3.0 配 voice 0.3.0，必含 resume_strategy/member_card；0.1.0/0.2.0 配旧 voice 0.2.0，按旧行为读取；0.2.0 仍生成成员卡。新交付缺策略则失败，不能回退旧报告充当新版交付。
